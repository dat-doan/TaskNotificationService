Bức tranh toàn cảnh

Sau chặng nàybạn vẽ lại được sơ đồ ai gửi cho ai, và hiểu vì sao server không gửi thẳng tới điện thoại.

HọcPush và pull khác nhau thế nào

Có hai cách để app biết "có việc mới". Với pull, app cứ vài phút lại hỏi server "có gì mới không?". Cách này đơn giản nhưng tốn pin, tốn mạng, và chỉ chạy khi app đang mở. Với push, server chủ động báo cho thiết bị đúng lúc có chuyện, kể cả khi app đang đóng.

Ví von

Pull giống như cứ 5 phút bạn lại chạy ra cổng xem có thư chưa. Push giống như bưu tá bấm chuông khi có thư. Cách thứ hai đỡ mệt hơn nhiều, nhưng phải có một bưu tá. Trong thế giới push, "bưu tá" là dịch vụ của Google và Apple.

Vì sao server không gửi thẳng tới điện thoại

Điện thoại không có địa chỉ cố định. Nó đổi từ Wi-Fi sang 4G, nằm sau lớp NAT của nhà mạng, và hệ điều hành tắt app chạy nền để tiết kiệm pin. Nếu mỗi app tự giữ một kết nối tới server riêng của mình thì 50 app sẽ là 50 kết nối, và pin cạn rất nhanh.

Vì vậy hệ điều hành giữ một kết nối thường trực duy nhất tới dịch vụ push của hãng, mọi app dùng chung đường đó. Dịch vụ này gọi là push provider:

Nền tảngPush providerAi vận hành
AndroidFirebase Cloud Messaging (FCM)Google
iOS, iPadOS, macOSApple Push Notification service (APNs)Apple
Trình duyệt (Chrome, Firefox, Safari, Edge)Web Push: mỗi trình duyệt có push service riêngGoogle, Mozilla, Apple, Microsoft

Device token: địa chỉ nhận thư

Khi app xin quyền nhận thông báo, provider cấp cho cặp (app, thiết bị) một chuỗi dài gọi là device token (FCM gọi là registration token). Muốn gửi tới máy nào, bạn đưa token của máy đó cho provider. Một token FCM trông như thế này:

fMEz3h1bQ0uXo2k9Rr7d1P:APA91bHk3V0w9mJ2c8hQx5sZ…(khoảng 150 ký tự)
  • Mỗi app trên mỗi máy có token riêng. Một người dùng có điện thoại, iPad và Chrome trên laptop thì có 3 token.
  • Token có thể đổi khi cài lại app, xoá dữ liệu app, hoặc khi provider tự làm mới.
  • Gỡ app thì token chết. Lần sau bạn gửi vào token đó, provider báo lỗi "không còn đăng ký".

Ba vai trong hệ thống

Toàn bộ lộ trình xoay quanh sơ đồ dưới đây. Có hai pha: pha đăng ký (bước 1–3, xảy ra khi người dùng mở app) và pha gửi (bước A–C, xảy ra mỗi khi có chuyện cần báo).

  1. 1–2. App xin quyền, rồi xin provider một token. Provider trả token về.
  2. 3. App gửi token lên Push Service, kèm thông tin "token này của user nào". Service lưu vào database.
  3. A. Một hệ thống khác (Task API) cần báo cho user 42: nó gọi Push Service, không cần biết gì về token hay FCM.
  4. B. Push Service tìm các token của user 42, dựng nội dung, gửi cho provider.
  5. C. Provider đẩy thông báo xuống máy qua kết nối thường trực. Hệ điều hành hiển thị nó.

Vì sao lộ trình này dùng FCM cho cả ba nền tảng

FCM nhận một kiểu API duy nhất rồi tự chuyển tiếp: tới iOS qua APNs (bạn tải APNs key của Apple lên Firebase), tới trình duyệt qua Web Push. Người mới chỉ cần học một API và một thư viện firebase-admin. Khi đã vững, bạn có thể gọi APNs hoặc Web Push trực tiếp để bớt phụ thuộc Google. Kiến trúc service không đổi, chỉ thay "bộ gửi".

HọcServer, request và response

Server là một chương trình chạy liên tục, lắng nghe ở một cổng (port, ví dụ 3000). Client gửi tới một request, server trả lại một response. Ngôn ngữ chung của hai bên là HTTP. Nhìn dưới dạng chữ thô, một request trông như sau:

Request: app gửi token lên server
POST /devices HTTP/1.1                     ← method + đường dẫn
Host: push.example.com
Content-Type: application/json             ← header: thông tin kèm theo
Authorization: Bearer eyJhbGciOi…          ← header: "tôi là ai"

{"token":"fMEz3h1bQ0u…","platform":"android"}   ← body: dữ liệu
Response: server trả lời
HTTP/1.1 201 Created                       ← status code
Content-Type: application/json

{"id":17,"platform":"android"}

Biến môi trường: cấu hình nằm ngoài code

Mật khẩu database, khoá API, đường dẫn file bí mật... khác nhau giữa máy bạn và server thật, và không được nằm trong Git. Ta để chúng trong biến môi trường. Lúc phát triển, ghi vào file .env (đã cho vào .gitignore). File src/config.ts đọc file đó khi app khởi động và kiểm tra bằng Zod: thiếu biến nào thì app dừng ngay, báo rõ thiếu gì.

Ví von

Node.js xử lý nhiều request cùng lúc giống một người phục vụ bàn giỏi: đặt món xong cho bàn 1 thì không đứng chờ bếp, mà đi nhận món bàn 2. Khi bếp báo xong (database trả kết quả) thì quay lại bàn 1. Vì thế code Node đầy async/await: mỗi chữ await là một lần "đi làm việc khác trong lúc chờ".

Fastify: bộ khung gọn nhẹ

Node.js có sẵn module http, nhưng tự tách đường dẫn, tự ghép body, tự ghi log cho từng request thì rất mệt. Fastify lo những việc đó: bạn khai báo "đường dẫn này thì gọi hàm này", nó lo phần còn lại, kèm sẵn bộ ghi log và cách test API mà không cần mở cổng. Fastify không áp đặt cấu trúc: chia file thế nào là do bạn. Lộ trình này dùng một quy ước đơn giản, mỗi thứ một chỗ cố định:

Sau này gặp NestJS ở công ty thì đó là một khung lớn hơn, tự tạo và nối các class giúp bạn bằng decorator @. Các khái niệm ở đây (route, kiểm tra dữ liệu, gác cửa, service, repository) vẫn y nguyên, chỉ khác cách viết.

Truyền phụ thuộc bằng tay

Một class không tự new những thứ nó cần. Nó khai báo trong constructor "tôi cần một Pool kết nối database". Ở một chỗ duy nhất là main.ts, ta tạo Pool đúng một lần rồi đưa vào mọi nơi cần. Kỹ thuật này gọi là dependency injection (DI). Không cần thư viện nào: chỉ là truyền tham số.

// src/devices/devices.repository.ts
export class DevicesRepository {
  // Không có "new Pool()" ở đây: ai dùng class này thì đưa Pool vào
  constructor(private readonly db: Pool) {}
}

// src/main.ts: nơi duy nhất "lắp ráp"
const db = new Pool({ connectionString: config.DATABASE_URL });
const devices = new DevicesRepository(db);

private readonly db: Pool trong constructor là cách viết tắt của TypeScript: vừa khai báo tham số, vừa lưu nó thành this.db.

Ví von

Đầu bếp không tự đi chợ. Đầu bếp ghi "cần cà chua, thịt bò", quản lý bếp (main.ts) lo mua và đặt sẵn lên bàn. Muốn đổi nhà cung cấp, hoặc thay bằng đồ giả để tập nấu (viết test), chỉ quản lý phải đổi, đầu bếp không sửa gì. Bạn sẽ thấy lợi ích này rõ nhất ở chặng 8 khi viết test.

export async function getPushToken(): Promise<string | null> {
  // Android 13+ phải xin quyền POST_NOTIFICATIONS
  if (Platform.OS === 'android' && Platform.Version >= 33) {
    await PermissionsAndroid.request(PermissionsAndroid.PERMISSIONS.POST_NOTIFICATIONS);

export class FcmService {

Upsert: thêm mới hoặc cập nhật trong một câu lệnh

App sẽ gửi token lên mỗi lần mở. Hãy xem ba tình huống:

  • Token mới tinh → thêm dòng mới.
  • Token đã có, cùng user → không thêm dòng trùng, chỉ cập nhật last_seen_at.
  • Token đã có, khác user (A đăng xuất, B đăng nhập trên cùng máy) → chuyển token sang user B, để A không nhận nhầm thông báo của B.

Cả ba được xử lý bằng một câu INSERT … ON CONFLICT (token) DO UPDATE, gọi là upsert (update + insert).

Tham số hoá câu SQL: chống SQL injection

Đừng bao giờ ghép chuỗi người dùng gửi vào câu SQL. Nếu ai đó gửi token là x'; DROP TABLE devices; --, câu lệnh ghép chuỗi sẽ xoá bảng của bạn. Thay vào đó dùng tham số $1, $2; thư viện pg gửi giá trị riêng, database không bao giờ hiểu nhầm nó là lệnh.

// SAI: ghép chuỗi
db.query(`SELECT * FROM devices WHERE token = '${token}'`);
// ĐÚNG: tham số hoá
db.query('SELECT * FROM devices WHERE token = $1', [token]);

    src/devices/devices.repository.ts
    import type { Pool } from 'pg';
import type { Platform } from './devices.schemas';

export class DevicesRepository {
  // Không tự mở kết nối: nhận Pool từ bên ngoài (main.ts tạo, đưa vào)
  constructor(private readonly db: Pool) {}

  async upsert(userId: string, token: string, platform: Platform, appVersion?: string) {
    const { rows } = await this.db.query(
      `INSERT INTO devices (user_id, token, platform, app_version)
       VALUES ($1, $2, $3, $4)
       ON CONFLICT (token) DO UPDATE
         SET user_id      = EXCLUDED.user_id,
             platform     = EXCLUDED.platform,
             app_version  = EXCLUDED.app_version,
             last_seen_at = now()
       RETURNING id, user_id, platform, last_seen_at`,
      [userId, token, platform, appVersion ?? null],
    );
    return rows[0];
  }

  async tokensOf(userId: string): Promise<string[]> {
    const { rows } = await this.db.query<{ token: string }>(
      'SELECT token FROM devices WHERE user_id = $1',
      [userId],
    );
    return rows.map((r) => r.token);
  }

  async removeTokens(tokens: string[]) {
    if (tokens.length === 0) return;
    await this.db.query('DELETE FROM devices WHERE token = ANY($1)', [tokens]);
  }

  async removeToken(token: string, userId?: string) {
    // Có userId thì chỉ xoá khi token thuộc đúng người đó
    await this.db.query(
      'DELETE FROM devices WHERE token = $1 AND ($2::text IS NULL OR user_id = $2)',
      [token, userId ?? null],
    );
  }
}

    EXCLUDED là dòng bạn vừa định thêm vào. Câu SET user_id = EXCLUDED.user_id nghĩa là "lấy user_id mới ghi đè lên cái cũ".

import { ZodError } from 'zod';

// Ném lỗi này ở bất kỳ đâu (route, service) để trả về status mong muốn.
// Ví dụ: throw new HttpError(404, 'no_devices')
export class HttpError extends Error {
  constructor(
    readonly statusCode: number,
    message: string,
  ) {
    super(message);
  }
}

// Một chỗ duy nhất đổi lỗi thành response JSON
export function errorHandler(err: unknown, req: FastifyRequest, reply: FastifyReply) {
  if (err instanceof ZodError) {
    // Dữ liệu gửi lên sai: liệt kê từng field sai để người gọi biết đường sửa
    return reply.code(400).send({
      error: 'invalid_request',
      issues: err.issues.map((i) => ({ field: i.path.join('.'), message: i.message })),
    });
  }
  // HttpError của bạn, hoặc lỗi có sẵn của Fastify (ví dụ body không phải JSON), đều có statusCode
  if (err instanceof Error && 'statusCode' in err && typeof err.statusCode === 'number' && err.statusCode < 500) {
    return reply.code(err.statusCode).send({ error: err.message });
  }
  // Còn lại là lỗi của server: ghi log đầy đủ để sửa, nhưng không lộ chi tiết ra ngoài
  req.log.error(err);
  return reply.code(500).send({ error: 'internal_error' });
}

  2. Viết hai hook xác thực

    Hook preHandler là người gác cửa: Fastify gọi nó trước handler. Hook chạy xong bình thường thì request đi tiếp; hook ném HttpError(401) thì request dừng lại và error handler trả 401.

    src/auth/auth.ts
    import { timingSafeEqual } from 'node:crypto';
import type { FastifyRequest } from 'fastify';
import { HttpError } from '../common/errors';

// Báo cho TypeScript: request có thêm field userId (requireUser gán vào)
declare module 'fastify' {
  interface FastifyRequest {
    userId: string;
  }
}

// Kiểu chung của hai hook bên dưới: nhận request, không hợp lệ thì ném lỗi
export type AuthHook = (req: FastifyRequest) => Promise<void>;

// Cho service nội bộ: so khớp header X-API-Key
export function apiKeyAuth(apiKey: string): AuthHook {
  const expected = Buffer.from(apiKey);
  return async (req) => {
    const given = Buffer.from(String(req.headers['x-api-key'] ?? ''));
    // timingSafeEqual so sánh mất thời gian như nhau dù sai ở ký tự nào,
    // kẻ xấu không đo thời gian để đoán dần từng ký tự được
    if (given.length !== expected.length || !timingSafeEqual(given, expected)) {
      throw new HttpError(401, 'unauthorized');
    }
  };
}

// Cho app: kiểm tra JWT do hệ thống đăng nhập phát hành.
// req.jwtVerify() (từ @fastify/jwt) đọc header "Authorization: Bearer …",
// kiểm tra chữ ký và hạn dùng; sai thì ném lỗi
export const requireUser: AuthHook = async (req) => {
  try {
    const payload = await req.jwtVerify<{ sub?: string }>();
    if (!payload.sub) throw new Error('JWT thiếu sub');
    req.userId = payload.sub; // sub = id người dùng, gắn vào request cho handler dùng
  } catch {
    throw new HttpError(401, 'unauthorized');
  }
};

    Ví dụ này dùng khoá chung HS256 cho đơn giản. Nếu hệ thống đăng nhập của bạn (Auth0, Firebase Auth, Cognito…) ký bằng RS256, cấu hình @fastify/jwt với public key của họ, hoặc dùng thêm gói get-jwks để tự tải khoá từ địa chỉ JWKS của họ.

    import { HttpError } from '../common/errors';
import type { DevicesRepository } from '../devices/devices.repository';
import { type FcmService, isDeadToken } from '../fcm/fcm.service';
import type { SendNotification } from './notifications.schemas';

export class NotificationsService {
  constructor(
    private readonly devices: DevicesRepository,
    private readonly fcm: FcmService,
  ) {}

  async send(input: SendNotification) {
    const { userId, ...payload } = input;
    const tokens = await this.devices.tokensOf(userId);
    if (tokens.length === 0) throw new HttpError(404, 'no_devices');

    const results = await this.fcm.sendToTokens(tokens, payload);
    const dead = results.filter((r) => isDeadToken(r.errorCode)).map((r) => r.token);
    await this.devices.removeTokens(dead); // dọn token chết ngay khi FCM báo

    return {
      sent: results.filter((r) => r.ok).length,
      failed: results.filter((r) => !r.ok).length,
      removedTokens: dead.length,
    };
  }
}

Hàng đợi & worker

Sau chặng nàyAPI trả lời 202 trong vài mili giây; một tiến trình worker riêng gửi thông báo ở nền và tự thử lại khi FCM lỗi.

HọcĐồng bộ và bất đồng bộ

Ý tưởng chính: tách việc nhận yêu cầu khỏi việc thực hiện yêu cầu. API chỉ ghi lại "có việc cần làm" rồi trả lời ngay. Một chương trình khác làm việc đó sau.

Ví von

Ở quán cà phê đông khách, thu ngân không tự pha từng ly. Họ nhận order, in phiếu, đưa bạn số thứ tự (đó là 202 Accepted kèm jobId), rồi phục vụ người tiếp theo. Phiếu xếp hàng trên quầy (queue), mấy người pha chế (worker) lấy phiếu ra làm lần lượt. Đông khách thì thêm người pha chế, không cần thêm thu ngân.

Redis là một kho dữ liệu chạy trong bộ nhớ, rất nhanh. BullMQ là thư viện Node dùng Redis làm hàng đợi, lo sẵn retry, hẹn giờ, chống trùng.

Retry với exponential backoff

Khi FCM quá tải, thử lại ngay lập tức chỉ làm nó quá tải thêm. Exponential backoff nghĩa là mỗi lần thất bại, chờ gấp đôi lần trước. Hệ thống có thời gian hồi phục, và job vẫn được gửi sớm nhất có thể.

Lỗi nào nên thử lại

Chỉ thử lại lỗi tạm thời (FCM sập, mạng chập, bị giới hạn tốc độ). Lỗi vĩnh viễn (user không có máy nào, payload sai) thử bao nhiêu lần cũng vậy, chỉ tốn tài nguyên. BullMQ có UnrecoverableError: ném lỗi này thì job vào failed luôn, không thử lại.

Sự thật khó chịu

Hàng đợi đảm bảo at-least-once: mỗi job chạy ít nhất một lần. Nếu worker gửi xong nhưng sập trước khi kịp báo "xong", job sẽ chạy lại và người dùng nhận hai thông báo. Chặng 6 xử lý chuyện này.

Một codebase, hai tiến trình

API và worker dùng chung code nhưng khởi động từ hai file khác nhau. API chạy main.ts: lắp ráp các phần, gọi buildApp() và mở cổng HTTP. Worker chạy worker.ts: lắp ráp những phần nó cần, tạo một Worker của BullMQ, không mở cổng nào, chỉ lấy job từ Redis. Hai bên dùng chung các phần nền.

  4. Viết hàm xử lý job

    src/worker/notifications.processor.ts
    import { type Job, UnrecoverableError } from 'bullmq';
import type { DevicesRepository } from '../devices/devices.repository';
import { type FcmService, isDeadToken, isRetryable } from '../fcm/fcm.service';
import type { SendJob } from '../queue/queue';

type Deps = { devices: DevicesRepository; fcm: FcmService };

// Trả về hàm xử lý một job. Phụ thuộc được đưa vào từ worker.ts
export function createProcessor({ devices, fcm }: Deps) {
  return async (job: Job<SendJob>) => {
    const { userId, ...payload } = job.data;
    const tokens = await devices.tokensOf(userId);
    if (tokens.length === 0) {
      // Lỗi vĩnh viễn: thử lại cũng vô ích
      throw new UnrecoverableError(`User ${userId} chưa có thiết bị`);
    }

    const results = await fcm.sendToTokens(tokens, payload);
    await devices.removeTokens(results.filter((r) => isDeadToken(r.errorCode)).map((r) => r.token));

    // Mọi thiết bị đều lỗi tạm thời: ném lỗi để BullMQ thử lại sau
    if (results.every((r) => isRetryable(r.errorCode))) {
      throw new Error('FCM đang lỗi tạm thời');
    }
    return { sent: results.filter((r) => r.ok).length };
  };
}

    createProcessor nhận phụ thuộc rồi trả về một hàm. BullMQ gọi hàm đó cho từng job. Hàm chạy xong là job xong; ném lỗi nghĩa là "job này hỏng, thử lại sau".

Sau chặng nàymỗi thông báo có id và trạng thái tra cứu được; gọi lại cùng một yêu cầu không gửi trùng; retry chỉ gửi lại cho máy chưa nhận.

HọcVì sao phải lưu lịch sử

  • Hỗ trợ người dùng: "Hôm qua tôi không nhận được nhắc deadline". Có lịch sử, bạn tra được ngay: gửi lúc nào, tới máy nào, lỗi gì.
  • Retry thông minh: biết máy nào đã nhận để lần sau chỉ gửi cho máy còn lại.
  • Chống gửi trùng: biết yêu cầu này đã nhận chưa.
  • Thống kê: bao nhiêu phần trăm thông báo được mở.

Mô hình dữ liệu

Trạng thái là một state machine

Một thông báo chỉ được đi theo những mũi tên cho phép. Viết rõ ra như dưới đây giúp bạn không bao giờ có thông báo "đã gửi rồi lại quay về đang chờ".

Idempotency: gọi hai lần, kết quả như gọi một lần

Task API gọi bạn, mạng chập đúng lúc bạn trả lời. Task API không biết bạn đã nhận chưa nên gọi lại. Không có biện pháp gì thì người dùng nhận hai thông báo giống hệt.

Cách giải: người gọi gửi kèm header Idempotency-Key, một chuỗi duy nhất cho mỗi ý định gửi (ví dụ due-soon:t_8421). Database có ràng buộc UNIQUE trên cột này, nên lần thứ hai không tạo được bản ghi mới, và bạn trả lại kết quả của lần đầu.

Ví von

Chuyển khoản ngân hàng có mã giao dịch. Bấm "Chuyển" hai lần vì mạng lag, ngân hàng thấy cùng mã thì chỉ trừ tiền một lần. Idempotency-Key chính là mã giao dịch đó.

"Đã gửi" không có nghĩa là "đã đọc"

FCM trả về thành công chỉ có nghĩa là FCM đã nhận tin. Máy có thể đang tắt (FCM giữ tin một thời gian, mặc định tối đa 4 tuần), người dùng có thể tắt thông báo của app trong cài đặt. Muốn biết người dùng có mở không, app phải tự báo về khi họ bấm vào.

    src/notifications/notifications.repository.ts
    import type { Pool } from 'pg';
import type { SendResult } from '../fcm/fcm.service';

export type NotificationRow = {
  id: string; user_id: string; title: string; body: string;
  data: Record<string, string>; status: string; opened_at: Date | null;
};

export type NewNotification = {
  userId: string; title: string; body: string; data?: Record<string, string>;
  sendAt?: Date; status?: 'queued' | 'scheduled'; // dùng ở chặng 7
};

export class NotificationsRepository {
  constructor(private readonly db: Pool) {}

  async create(n: NewNotification, idempotencyKey: string | null) {
    const { rows } = await this.db.query<{ id: string; status: string }>(
      `INSERT INTO notifications (user_id, title, body, data, idempotency_key, send_at, status)
       VALUES ($1, $2, $3, $4, $5, $6, $7)
       ON CONFLICT (idempotency_key) DO NOTHING
       RETURNING id, status`,
      [n.userId, n.title, n.body, n.data ?? {}, idempotencyKey, n.sendAt ?? null, n.status ?? 'queued'],
    );
    if (rows[0]) return { ...rows[0], duplicate: false };
    // Trùng key: trả lại bản đã có, không tạo mới
    const existing = await this.db.query<{ id: string; status: string }>(
      'SELECT id, status FROM notifications WHERE idempotency_key = $1',
      [idempotencyKey],
    );
    return { ...existing.rows[0], duplicate: true };
  }

  async findById(id: string) {
    const { rows } = await this.db.query<NotificationRow>('SELECT * FROM notifications WHERE id = $1', [id]);
    return rows[0] ?? null;
  }

  async setStatus(id: string, status: string) {
    await this.db.query('UPDATE notifications SET status = $2, updated_at = now() WHERE id = $1', [id, status]);
  }

  async sentTokens(notificationId: string): Promise<Set<string>> {
    const { rows } = await this.db.query<{ token: string }>(
      `SELECT token FROM deliveries WHERE notification_id = $1 AND status = 'sent'`,
      [notificationId],
    );
    return new Set(rows.map((r) => r.token));
  }

  async saveDelivery(notificationId: string, r: SendResult) {
    await this.db.query(
      `INSERT INTO deliveries (notification_id, token, status, fcm_message_id, error_code)
       VALUES ($1, $2, $3, $4, $5)
       ON CONFLICT (notification_id, token) DO UPDATE
         SET status         = EXCLUDED.status,
             fcm_message_id = EXCLUDED.fcm_message_id,
             error_code     = EXCLUDED.error_code,
             attempts       = deliveries.attempts + 1,
             updated_at     = now()`,
      [notificationId, r.token, r.ok ? 'sent' : 'failed', r.messageId ?? null, r.errorCode ?? null],
    );
  }

  async deliveriesOf(notificationId: string) {
    // Cắt ngắn token: không lộ token đầy đủ ra ngoài
    const { rows } = await this.db.query(
      `SELECT left(token, 10) || '…' AS token, status, error_code, attempts, updated_at
       FROM deliveries WHERE notification_id = $1`,
      [notificationId],
    );
    return rows;
  }

  async markOpened(id: string, userId: string) {
    await this.db.query(
      `UPDATE notifications SET opened_at = now()
       WHERE id = $1 AND user_id = $2 AND opened_at IS NULL`,
      [id, userId],
    );
  }
}

    import type { Job } from 'bullmq';
import type { DevicesRepository } from '../devices/devices.repository';
import { type FcmService, isDeadToken, isRetryable } from '../fcm/fcm.service';
import type { NotificationsRepository } from '../notifications/notifications.repository';
import type { SendJob } from '../queue/queue';

type Deps = { devices: DevicesRepository; notifications: NotificationsRepository; fcm: FcmService };

export function createProcessor({ devices, notifications, fcm }: Deps) {
  return async (job: Job<SendJob>) => {
    const n = await notifications.findById(job.data.notificationId);
    if (!n || n.status === 'canceled') return { status: 'skipped' };

    await notifications.setStatus(n.id, 'processing');
    const tokens = await devices.tokensOf(n.user_id);
    const alreadySent = await notifications.sentTokens(n.id); // các lần thử trước đã gửi xong
    const pending = tokens.filter((t) => !alreadySent.has(t));

    const results = await fcm.sendToTokens(pending, {
      title: n.title,
      body: n.body,
      data: { ...n.data, notificationId: n.id }, // app cần id để báo "đã mở"
    });
    for (const r of results) await notifications.saveDelivery(n.id, r);
    const dead = results.filter((r) => isDeadToken(r.errorCode)).map((r) => r.token);
    await devices.removeTokens(dead);

    // Còn máy lỗi tạm thời và còn lượt: ném lỗi để thử lại (chỉ máy đó)
    const hasMoreAttempts = job.attemptsMade + 1 < (job.opts.attempts ?? 1);
    if (hasMoreAttempts && results.some((r) => isRetryable(r.errorCode))) {
      throw new Error('Còn thiết bị lỗi tạm thời, sẽ thử lại');
    }

    const sent = alreadySent.size + results.filter((r) => r.ok).length;
    const total = tokens.length - dead.length;
    const status = sent === 0 ? 'failed' : sent < total ? 'partially_sent' : 'sent';
    await notifications.setStatus(n.id, status);
    return { status, sent, total };
  };
}

Tính năng thật

Sau chặng nàynhắc deadline gửi đúng giờ và huỷ được; nội dung theo ngôn ngữ người dùng; tôn trọng cài đặt tắt thông báo và giờ yên tĩnh.

Chặng này gồm nhiều tính năng nhỏ, độc lập nhau. Mỗi tính năng là một quyết định nằm trên đường đi của một yêu cầu gửi:

Học1. Hẹn giờ và huỷ

Kịch bản: người dùng tạo task hạn 10:00, muốn được nhắc trước 30 phút. Task API gọi bạn ngay lúc tạo task, kèm sendAt: "2026-11-19T09:30:00+07:00". Bạn tính delay = sendAt − bây giờ và đưa job vào hàng với delay. BullMQ giữ job ở trạng thái delayed, đến giờ mới cho worker lấy.

  • Người dùng đánh dấu xong task trước 9:30 → Task API gọi DELETE /notifications/:id.
  • Người dùng dời hạn sang 15:00 → huỷ cái cũ, tạo cái mới với Idempotency-Key khác (ví dụ due-soon:t_8421:v2).

Job hẹn giờ nằm trong Redis. Hẹn vài giờ, vài ngày thì ổn. Với lịch hẹn rất xa (vài tháng) hoặc rất nhiều, nhiều đội chọn lưu ở database và có một tác vụ quét định kỳ đưa vào hàng khi gần đến giờ. Thông báo lặp lại (bản tin hằng ngày) thì dùng job scheduler của BullMQ.

// Trả về số mili giây cần lùi lại. 0 nghĩa là gửi được ngay.
export function quietDelayMs(at: Date, s: UserSettings): number {
  if (s.quiet_start === null || s.quiet_end === null) return 0;

  const parts = new Intl.DateTimeFormat('en-US', {
    timeZone: s.timezone, hour: 'numeric', minute: 'numeric', hourCycle: 'h23',
  }).formatToParts(at);
  const h = Number(parts.find((p) => p.type === 'hour')?.value);
  const m = Number(parts.find((p) => p.type === 'minute')?.value);

  const start = s.quiet_start;
  const end = s.quiet_end;
  // Khung yên tĩnh có thể vắt qua nửa đêm (22 → 7)
  const inQuiet = start < end ? h >= start && h < end : h >= start || h < end;
  if (!inQuiet) return 0;

  const minutesLeft = (end * 60 - (h * 60 + m) + 1440) % 1440;
  return minutesLeft * 60_000;
}

      [userId],

  // Cho phép tối đa `limit` thông báo mỗi `windowSec` giây cho một người
  async allowForUser(userId: string, limit = 10, windowSec = 3600) {
    const key = `rl:push:${userId}`;
    const count = await this.redis.incr(key);                 // tăng bộ đếm, trả về giá trị mới
    if (count === 1) await this.redis.expire(key, windowSec); // lần đầu: đặt hạn 1 giờ
    return count <= limit;
  }

    src/notifications/notifications.service.ts (thay toàn bộ)
    import type { Queue } from 'bullmq';
import { HttpError } from '../common/errors';
import type { SendJob } from '../queue/queue';
import type { NotificationsRepository } from './notifications.repository';
import type { SendNotification } from './notifications.schemas';
import { quietDelayMs } from './quiet-hours';
import type { RulesService } from './rules.service';
import { render } from './templates';

export class NotificationsService {
  constructor(
    private readonly repo: NotificationsRepository,
    private readonly rules: RulesService,
    private readonly queue: Queue<SendJob>,
  ) {}

  async create(input: SendNotification, idempotencyKey: string | null) {
    const urgent = input.category === 'reminder';

    // 1. Người dùng đã tắt loại thông báo này?
    if (!(await this.rules.isCategoryEnabled(input.userId, input.category))) {
      return { status: 'skipped', reason: 'user_opted_out', duplicate: false };
    }
    // 2. Quá nhiều thông báo không gấp trong 1 giờ?
    if (!urgent && !(await this.rules.allowForUser(input.userId))) {
      throw new HttpError(429, 'rate_limited');
    }
    // 3. Dựng nội dung từ template
    const { title, body } = render(input.template, input.locale, input.vars);

    // 4. Tính giờ gửi: lấy sendAt (không sớm hơn bây giờ), rồi lùi qua giờ yên tĩnh
    const now = Date.now();
    const base = new Date(Math.max(input.sendAt ? Date.parse(input.sendAt) : now, now));
    const quiet = urgent ? 0 : quietDelayMs(base, await this.rules.userSettings(input.userId));
    const sendAt = new Date(base.getTime() + quiet);
    const delay = sendAt.getTime() - now;

    const n = await this.repo.create(

  3. Tắt êm (graceful shutdown): không bỏ dở job

    Khi deploy bản mới, nền tảng gửi tín hiệu SIGTERM cho tiến trình cũ. Fastify và BullMQ không tự bắt tín hiệu này; bạn viết vài dòng để tắt đúng thứ tự:

    • API: app.close() ngừng nhận request mới, đợi request đang chạy xong, rồi chạy hook onClose để đóng hàng đợi, Redis và pool PostgreSQL.
    • Worker: worker.close() ngừng nhận job mới, đợi job đang chạy xong, rồi đóng pool.

    import { Worker } from 'bullmq';
import { Pool } from 'pg';
import { pino } from 'pino';
import { config } from './config';
import { DevicesRepository } from './devices/devices.repository';
import { FcmService } from './fcm/fcm.service';
import { NotificationsRepository } from './notifications/notifications.repository';
import { NOTIFICATIONS_QUEUE, type SendJob } from './queue/queue';
import { createProcessor } from './worker/notifications.processor';

const log = pino({ name: 'worker', level: config.LOG_LEVEL });

async function main() {
  const db = new Pool({ connectionString: config.DATABASE_URL, max: 10 });
  const devices = new DevicesRepository(db);
  const notifications = new NotificationsRepository(db);
  const fcm = new FcmService(config.FIREBASE_CREDENTIALS);

  const worker = new Worker<SendJob>(
    NOTIFICATIONS_QUEUE,
    createProcessor({ devices, notifications, fcm }),
    { connection: { host: config.REDIS_HOST, port: config.REDIS_PORT }, concurrency: 10 },
  );

  // Log có cấu trúc: object trước, câu mô tả sau
  worker.on('completed', (job, result) => {
    log.info({ notificationId: job.data.notificationId, ...result }, 'đã xử lý thông báo');
  });
  worker.on('failed', (job, err) => {
    log.warn({ jobId: job?.id, attempt: job?.attemptsMade, err: err.message }, 'job lỗi');
    // Lỗi bất ngờ ở lần cuối (mạng, database): đánh dấu failed để không kẹt ở processing
    if (job && job.attemptsMade >= (job.opts.attempts ?? 1)) {
      notifications.setStatus(job.data.notificationId, 'failed').catch((e) => log.error(e));
    }
  });

  // Nền tảng gửi SIGTERM khi deploy bản mới; Ctrl+C gửi SIGINT
  for (const signal of ['SIGTERM', 'SIGINT'] as const) {
    process.once(signal, async () => {
      log.info({ signal }, 'đang tắt êm…');
      await worker.close(); // ngừng nhận job mới, đợi job đang chạy xong
      await db.end();
      process.exit(0);
    });
  }
  log.info('Worker đã sẵn sàng, đang chờ job…');
}

    docker compose up -d --build --scale worker=3

    Biến trong environment thắng biến trong .env, nên trong Docker, DATABASE_URL và REDIS_HOST trỏ tới tên container thay vì localhost. Image cuối chỉ chứa dist/ và thư viện chạy, không có .env hay mã nguồn TypeScript.

    Trên production, bật chế độ lưu xuống đĩa cho Redis để job không mất khi Redis khởi động lại: command: ["redis-server", "--appendonly", "yes"]. BullMQ cũng khuyên đặt maxmemory-policy noeviction để Redis không tự xoá job khi đầy bộ nhớ.
